## 1. Crawlability & Indexation

### 1.1 robots.txt — usable, minor concerns

File: `public/robots.txt`. Built by `next-sitemap` per `next-sitemap.config.js:10-21`.

What works:
- `Host: https://www.bestbottles.com` directive present (`public/robots.txt:26`)
- AI crawlers explicitly allowed: `GPTBot`, `Google-Extended`, `anthropic-ai` (`public/robots.txt:13-23`) — solid GEO/AEO foundation
- Crawl-disallows for `/api/`, `/portal/`, `/studio/`, `/sign-in/`, `/_next/`

What's weak:
- Two `User-agent: *` blocks (`public/robots.txt:2` and `:6`) — technically valid but redundant; consolidate into one block to avoid parser-specific edge cases.
- Missing disallows for `/sign-up/`, `/cart`, `/grace-workspace`, `/tech-stack`, `/example`, `/fitment-demo`. Some of these are excluded from the sitemap (`next-sitemap.config.js:23-30`) but not from robots — Google may still discover and crawl them via internal navigation or external links.
- No `Disallow: /*?*` for parametered URLs — see Section 8 (Crawl Waste).

### 1.2 Sitemap generation — there are TWO sitemaps and they don't agree

The site has two competing sitemap sources:

1. **Static sitemap** generated by `next-sitemap` at build time (`next-sitemap.config.js`). Output: `public/sitemap.xml` (index) + `public/sitemap-0.xml` (21 URLs, static routes only).
2. **Server-side dynamic sitemap** at `src/app/server-sitemap.xml/route.ts:9-45` that queries Convex for product groups (`api.products.getAllCatalogGroups`) and Sanity for blog posts.

The `next-sitemap` config references the server route via `additionalSitemaps: ["https://www.bestbottles.com/server-sitemap.xml"]` (`next-sitemap.config.js:18-20`), which is correct in principle. But:

- The P0 ticket BB-SEO-004 noted only 21 URLs in the static sitemap; this is true and expected for the static side. The dynamic `/server-sitemap.xml` route exists and should add ~2,300 product URLs IF it's running correctly in production.
- **Risk:** The dynamic route uses `process.env.NEXT_PUBLIC_CONVEX_URL` (`src/app/server-sitemap.xml/route.ts:7`). If Convex returns slowly or times out in the serverless function, Google will get an empty or partial sitemap. There's no caching, no `revalidate`, no fallback. Every crawler hit re-queries Convex.
- **Risk:** The route does not include `/collections/*` URLs (only one collection page exists today — `boston-round-30ml` — and it's a 308 redirect to `/catalog?families=Boston%20Round&search=30ml`, see `src/app/collections/boston-round-30ml/page.tsx:1-5`).
- **Risk:** Product group slugs only, not SKU-level URLs. With 2,354 SKUs and 225 product groups, the dynamic sitemap will emit ~225 URLs, not 2,354. PDPs are group-level so this is acceptable for indexation but worth confirming the count target in BB-SEO-004 says "2,400+ URLs" — the realistic number is closer to 250-300 (225 groups + 30 collections + 9 blog + ~10 static).

**See new ticket BB-SEO-201** below.

### 1.3 Internal linking — Footer is shallow, Navbar is JS-heavy

Footer (`src/components/HomePage.tsx:873-937`):
- **Shop column links all dead-end at `/catalog`** (lines 896-901). "By Usage", "By Product Type", "By Collection", "New Arrivals", "Best Sellers" all point to `/catalog` with no query string. Wasted internal-linking equity — every one of these should deep-link into a filtered catalog URL (e.g. `/catalog?applicators=spray`, `/catalog?families=Empire`, `/catalog?families=Boston%20Round`).
- **Privacy and Terms point to `/resources`** (lines 930-931) — that page isn't a privacy policy. Real legal pages don't exist. Either build them or remove the links.
- **Social URLs disagree with `lib/seo.ts`**: footer points to `instagram.com/nematinternational` and `linkedin.com/company/nematinternational`; `src/lib/seo.ts:35-38` says `instagram.com/bestbottles` and `linkedin.com/company/nemat-international` (different IG handle). Pick one source of truth.
- **Email mismatch (already P1-4):** footer uses `sales@nematinternational.com` (`src/components/HomePage.tsx:927`); `src/lib/seo.ts:42` uses `sales@bestbottles.com`.

Navbar (`src/components/Navbar.tsx:1`) is a Client Component. Mega-menu panels come from Sanity server-side via `getMegaMenuPanels()` in `src/app/layout.tsx:95` and are passed through `AppProviders`, so the link structure is in initial HTML — good for crawlers. Verify the actual rendered output of mega-menu items in production HTML (not just hydrated DOM).

### 1.5 Faceted navigation indexation plan — currently missing

The legacy `bestbottles.com` had 8 querystring filter dimensions creating ~thousands of crawlable filter URLs. The new `/catalog?families=…&applicators=…&capacities=…&colors=…&neckThreadSizes=…&priceMin=…&priceMax=…&componentType=…&search=…&sort=…&view=…&limit=…&page=…` permutation surface is even larger.

`src/app/catalog/page.tsx` reads all of these via `paramsToFilters()` (`src/app/catalog/page.tsx:1240`) and pushes them back via `pushToUrl()` (`src/app/catalog/page.tsx:1259-1267`) using `router.replace(...)` — so they're real, crawlable URLs once a bot lands on the catalog.

Without a strategy, Google will discover hundreds of `/catalog?…` URLs, all sharing the same `<title>` and `<meta description>` inherited from `layout.tsx`, all self-canonical to themselves (because no canonical override exists), all containing thin filtered product grids. **Classic crawl-budget waste.**

**Fix strategy (mandatory before launch):**
1. In `src/app/catalog/page.tsx`, add a server-side `generateMetadata` that sets `<link rel="canonical" href="https://www.bestbottles.com/catalog">` for **every** filter combination so all filtered views consolidate to the canonical catalog URL.
2. Add `<meta name="robots" content="noindex,follow">` when any filter param is present (only the bare `/catalog` URL stays indexable).
3. Whitelist a small set of high-intent filter combinations (e.g. `?families=Empire`, `?applicators=spray`, `?families=Boston%20Round`) and pre-render them as real, indexable destinations with hand-crafted titles. These become "collection pages" without needing a new route.

**See new ticket BB-SEO-202** below.

## 2. Schema / Structured Data

### 2.1 Sitewide schema is solid

`src/app/layout.tsx:100-107` injects `Organization` and `WebSite` JSON-LD on every page.

The `WebSite` block (`src/lib/seo.ts:47-63`) includes a `SearchAction` with `urlTemplate: ${SITE_URL}/catalog?search={search_term_string}` — correctly wired to the catalog's `search` query param. Google sitelinks searchbox is achievable.

The `Organization` block (`src/lib/seo.ts:20-45`) is incomplete (already documented as P1-1) — missing street address, phone, complete `sameAs`, multiple `contactPoint` channels.

### 2.2 PDP Product schema — the schema IS rendered, but only after client hydration

This is the single most important non-P0 finding in this audit.

`src/app/products/[slug]/page.tsx:925` declares the page as `export default function ProductDetailPage(...)` and the file starts with `"use client"` at line 1. The page calls `useQuery(api.products.getProductGroup, ...)` (`src/app/products/[slug]/page.tsx:934`) — a client-side Convex query.

The JSON-LD scripts are rendered in the React tree at `src/app/products/[slug]/page.tsx:1458-1469`:

```tsx
{jsonLd && (
    <script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }} />
)}
{breadcrumbJsonLd && (
    <script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(breadcrumbJsonLd) }} />
)}
```

And both `jsonLd` and `breadcrumbJsonLd` are gated on `selectedVariant` and `group` being non-null (`src/app/products/[slug]/page.tsx:1362-1388`). Those values come from the Convex `useQuery` — they DO NOT EXIST during server-side render. The initial HTML response from Vercel will contain a `PdpLoadingSkeleton` (`src/app/products/[slug]/page.tsx:891-921`, returned at line 1398) and NO Product JSON-LD.

**Googlebot does render JavaScript, but:**
- It's a second-pass render that can be days or weeks behind the first crawl
- Bingbot/DuckDuckBot/Yandex/older crawlers index the first-pass HTML only
- Most rich-result eligibility decisions are made on first-pass HTML
- Faceted competitors (SKS Bottle, Berlin Packaging) all serve SSR'd Product schema in initial HTML

**Worse:** the same `useEffect` block (`src/app/products/[slug]/page.tsx:1241-1274`) sets `document.title`, `meta[name="description"]`, and `link[rel="canonical"]` imperatively on the client. The initial HTML for `/products/empire-30ml-clear` contains the generic site title from `layout.tsx` (`"Best Bottles — Premium Glass Packaging…"`), not the product title. Crawlers see the generic title until the client JS runs.

**Fix:** Convert `/products/[slug]/page.tsx` from a Client Component to a Server Component shell with:
- `generateMetadata({ params })` that calls Convex via `ConvexHttpClient` server-side to fetch the product group and emit per-PDP `<title>`, `<meta description>`, `alternates.canonical`, and `openGraph.images[0].url`.
- Server-rendered Product + BreadcrumbList JSON-LD using `buildProductJsonLd()` and `buildBreadcrumbJsonLd()` from `src/lib/seo.ts`.
- Move the interactive variant-picker, image gallery, and add-to-cart logic into a `<ProductDetailClient>` child component.

This is the single biggest SEO win available before launch. **See new ticket BB-SEO-203** — recommend P1.

### 2.3 BreadcrumbList — present on PDP, missing elsewhere

`src/app/products/[slug]/page.tsx:1380-1388` builds a 4-level breadcrumb (Home → Catalog → Family → Product) using `buildBreadcrumbJsonLd()`. Good.

Missing breadcrumb JSON-LD on:
- `/catalog` (should be Home → Catalog)
- `/blog` (Home → Journal)
- `/blog/[slug]` (Home → Journal → Article Title)
- `/about`, `/resources`, `/contact`, `/request-quote`, `/request-sample` (Home → Page Name)

### 2.4 Article / BlogPosting schema — NOT rendered

`src/app/blog/[slug]/page.tsx:1-295` has `generateMetadata` for title/description/OG but **never injects Article or BlogPosting JSON-LD**. Search for `application/ld+json` in this file: zero results.

Without `BlogPosting` schema (or `Article`), the blog posts are ineligible for:
- Google Discover surface
- Top stories carousel
- "Article" rich snippets

**See new ticket BB-SEO-204.**

### 2.5 CollectionPage / ItemList schema — NOT rendered on /catalog

`src/lib/seo.ts:131-146` exports `buildCollectionPageJsonLd()` but it's never called. `src/app/catalog/page.tsx` does not import it (`Grep` returned zero matches for `buildCollectionPageJsonLd` in the catalog file). The 2,300+ products listed in the catalog have no `ItemList` schema to help Google understand the page as a product list.

**See new ticket BB-SEO-205.**

### 2.6 LocalBusiness, Product Review, FAQ — confirmed absent

- **LocalBusiness:** Union City, CA storefront has no schema (already P1-2).
- **AggregateRating / Review:** No reviews system in the codebase (`Grep` for "Review" or "AggregateRating" in `src/`: only documentation refs). Don't add fake ratings — if/when a reviews system ships, wire `AggregateRating` into `buildProductJsonLd()`.
- **FAQPage:** `src/app/resources/page.tsx:49-57` has 7 inline FAQ items hardcoded but they're not wrapped in `FAQPage` schema. **See new ticket BB-SEO-206.**

No duplicate or contradictory schema in the codebase. Organization is rendered once per page (in root layout). Product is rendered once per PDP. Good hygiene.

### 3.3 Canonical correctness

Root layout sets `alternates: { canonical: SITE_URL }` (`src/app/layout.tsx:68`). That's the homepage canonical only. Per-route canonicals are not overridden in `generateMetadata` anywhere except client-side on PDPs (`src/app/products/[slug]/page.tsx:1255-1261`).

This means **every static page (`/catalog`, `/about`, `/blog`, etc.) currently emits a canonical of `https://bestbottles.company`** (the site URL constant) — pointing back to the homepage — unless the page-specific `metadata` export sets its own `alternates.canonical`. Spot-checked:
- `/about` — no canonical override → canonicalizes to homepage. **Wrong.**
- `/blog` — no canonical override → canonicalizes to homepage. **Wrong.**
- `/resources` — no canonical override → canonicalizes to homepage. **Wrong.**
- `/blog/[slug]` — no `alternates.canonical` in `generateMetadata` (`src/app/blog/[slug]/page.tsx:65-73`) → canonicalizes to homepage. **Wrong.**

**This is a P1.** Every page needs an explicit canonical to itself (or use `metadataBase` + relative paths). Currently search engines see homepage canonical on every URL, which will collapse the whole site to one indexed page.

**See new ticket BB-SEO-208.**

### 3.4 OG / Twitter card completeness

Root layout (`src/app/layout.tsx:69-83`) has full OG + Twitter cards with 1200×630 image. Blog posts override OG (`src/app/blog/[slug]/page.tsx:68-72`) but not Twitter — Twitter card falls back to the layout default, which references the generic OG image, not the post-specific one. Minor.

`/about`, `/resources`, `/blog` (index) — no OG override. They inherit the layout default. Acceptable but missed branding opportunity.

PDPs — no OG (client-side metadata doesn't set OG). Critical for social shares. Roll into BB-SEO-203 (PDP SSR conversion).

## 4. Performance / Core Web Vitals

### 4.1 Hero / LCP risks

`src/components/HomePage.tsx:161` renders the hero image with `priority` — good, LCP-focused. BUT: `unoptimized={!!imageUrl}` (`src/components/HomePage.tsx:161`) — when a Sanity hero image is set, `next/image` optimization is bypassed. The raw Sanity-CDN image (potentially 2MB+) is served directly. **Confirmed pattern across multiple Image components in the codebase.**

Recommendation: trust `cdn.sanity.io` (already in `next.config.ts:24-30` remotePatterns) and let `next/image` resize via the `_next/image` proxy. Remove `unoptimized` from hero images.

**See new ticket BB-SEO-209.**

### 4.2 Fonts

`src/app/layout.tsx:16-34` loads three font families via `next/font/google`: Cormorant (8 variants), EB Garamond (8 variants), Inter (5 variants). That's 21 font files in the critical CSS path. Each is `display: 'swap'` by default in `next/font` — minimal FOUT risk — but the byte cost is real.

Recommendation: audit actual font usage. If Cormorant italics are never used, drop them. If EB Garamond is only used in one component, lazy-load it via `next/dynamic` or scoped CSS.

### 4.3 INP risks — PDP is a 2,156-line client component

`src/app/products/[slug]/page.tsx` is 2,156 lines of `"use client"` code, with:
- `useQuery` from Convex (`src/app/products/[slug]/page.tsx:934`, line 962)
- 4+ `useMemo` selectors over variants (lines 985, 1002, 1042, 1048, 1066, 1090…)
- Mega `useEffect` for sticky bar tracking on scroll (lines 1331-1359)
- `framer-motion` animations on every variant tile (line 10)

This is a notable INP (Interaction to Next Paint) risk. Converting to a Server Component shell (per BB-SEO-203) would shed >50% of the client bundle.

### 4.4 Client-side data fetching that should be server-side

- `/products/[slug]` — Convex `useQuery` for product group (already covered).
- `/catalog/page.tsx:13` — Convex `useQuery` for the entire catalog. This means the catalog renders an empty skeleton on first paint and populates client-side. Initial HTML has zero product cards — bad for crawler discovery of internal links to PDPs.
- `/catalog/page.tsx:59-77` — Sanity client.fetch inside a `useEffect` for the family banner image. Should be server-side.

**See new ticket BB-SEO-210.**

### 4.5 next.config.ts image config

`next.config.ts:24-31` — only `cdn.sanity.io` is in remotePatterns. But the PDP uses `cdn.shopify.com` images via raw `<img>` tags (search for `cdn.shopify.com` in `src/app/products/[slug]/page.tsx` — many matches). The `eslint-disable @next/next/no-img-element` at line 11 of the PDP file confirms the team chose to bypass `next/image` for Shopify CDN images. That's an LCP miss on product images.

**See new ticket BB-SEO-211.**

## 6. Security Headers / HTTPS

### 6.1 Headers present in next.config.ts

`next.config.ts:88-101` defines:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Strict-Transport-Security: max-age=63072000; includeSubDomains` (2-year HSTS — good)
- `Permissions-Policy: camera=(), microphone=(self), geolocation=(), payment=(self), usb=()` — `microphone=(self)` is unusual; only needed if a feature uses mic (likely Grace voice). Confirm before launch.

### 6.2 Missing headers

- **No `Content-Security-Policy`** — even a permissive `default-src 'self' 'unsafe-inline' https:` would block injection attacks. Grace/Convex/Sanity/Shopify CDN need allowlisting. Defer to post-launch.
- **No `X-DNS-Prefetch-Control`**, **no `Cross-Origin-Opener-Policy`**, **no `Cross-Origin-Resource-Policy`** — minor, none are SEO-critical.
- **HSTS lacks `preload`** — once stable, add `preload` and submit to hstspreload.org.

### 6.3 HTTPS redirect

Vercel handles HTTPS at the platform layer. `vercel.json` is minimal (`vercel.json:1-9`) — just defines the build command and PDF function memory. Confirm in Vercel project settings that HTTPS-only is enabled and HTTP 308 redirects to HTTPS.

### 6.4 No www / non-www canonicalization rule in code

`next.config.ts:33-86` redirects only handle legacy PHP paths. Non-www → www should be DNS-level (Vercel auto-redirects when you configure a primary domain in the project settings). Confirm `bestbottles.com` is set as a 308 redirect to `www.bestbottles.com` in Vercel before launch. **See new ticket BB-SEO-212.**

## 9. New P1/P2/P3 Dev Tickets

All numbered to slot after BB-SEO-001 through BB-SEO-004 (P0) and BB-SEO-101 through BB-SEO-107 (P1 sketch in `p0-dev-tickets-urgent.md`).

### BB-SEO-201 · Dynamic sitemap reliability + collection URL coverage
**Priority:** P1 (4 hours)
**Evidence:** `src/app/server-sitemap.xml/route.ts:1-45` — no caching, no fallback, only product groups + blog posts, no static routes, no collections.
**Impact:** A Convex outage = empty sitemap. Google sees 21 URLs from the static sitemap and concludes the site is small. Discovery of 225 PDPs is delayed.
**Fix:**
- Add `export const revalidate = 3600` to the route (1-hour ISR cache).
- Wrap Convex/Sanity calls in `Promise.allSettled` so partial failures still emit a partial sitemap.

### BB-SEO-202 · Faceted-nav canonical + noindex strategy
**Priority:** P1 (3 hours)
**Evidence:** `src/app/catalog/page.tsx:1259-1267` pushes filter params via `router.replace` but has no `generateMetadata` to control canonical/robots per filter state.

export async function generateMetadata({ searchParams }): Promise<Metadata> {
  const hasFilters = Object.keys(searchParams).some(k =>
    ["families","applicators","capacities","colors","neckThreadSizes","priceMin","priceMax","search","sort","page","limit"].includes(k)

}

### Overall technical SEO readiness for June 15 launch: **62 / 100**

This score assumes the 4 P0 tickets in `p0-dev-tickets-urgent.md` are fixed before launch. Without those, the score drops to **24/100** and launch should be delayed.

The codebase has a **strong foundation** — Next.js Metadata API, centralized SEO library, structured-data builders, AI crawler allowlist, sensible URL structure, decent security headers. The gap is that **the most important page type (PDPs) is a Client Component that renders metadata and JSON-LD only after client hydration**, which means crawlers see a generic loading state. That single issue (BB-SEO-203) is worth ~15 points on the score.

### Top 5 wins to celebrate
1. **Centralized `lib/seo.ts`** (`src/lib/seo.ts:1-146`) with Organization, WebSite + SearchAction, BreadcrumbList, Product (with AggregateOffer + availability), CollectionPage builders. Most teams ship without this.

3. **Server-side legacy redirect map already in place** (`next.config.ts:33-86`) — `.php` URLs 301 to clean equivalents. Migration day will be smoother than 90% of CMS replatforms.

5. **Server-rendered mega-menu via Sanity** (`src/app/layout.tsx:95`) — internal nav links in initial HTML for crawler discovery. Many headless sites skip this.

### Top 5 risks if shipped as-is on 2026-06-15
1. **Per-page canonicals all point to homepage** (BB-SEO-208) — every URL emits `<link rel="canonical" href="https://www.bestbottles.com">`. 2. **PDP schema and metadata are client-rendered** (BB-SEO-203) — crawlers see a loading skeleton + generic title on first paint. Rich result eligibility delayed indefinitely; competitors out-rank by default.
3. **Faceted-nav URLs are self-canonical with no robots control** (BB-SEO-202) — hundreds of `?families=…&applicators=…&sort=…` URLs flood the crawl budget; thin, duplicate.
4. **Catalog page server-renders no product cards** (BB-SEO-210) — initial HTML is empty grid; PDP discovery relies on JS execution. Bing/Yandex/AI crawlers see nothing.
5. **`/collections/[slug]` route is vapor** (BB-SEO-217) — the URL pattern is referenced in strategy docs, sitemap plans, and internal expectations, but only one redirect-only file exists. Either build it or drop it.
